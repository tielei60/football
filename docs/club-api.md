# Club REST API

All responses JSON except authenticated match photo bytes; errors `{message}`. Session cookies sent automatically with same-origin fetch. All mutations require same-origin `Origin` (browser supplies it), or configured `FOOTBALL_PUBLIC_ORIGIN`. No public signup. CLI `FOOTBALL_ADMIN_USERNAME=owner FOOTBALL_ADMIN_PASSWORD='at least 10 chars' node server/bootstrap-admin.mjs` bootstraps first admin only.

### Matchday additions

- GET `/api/venues` -> Venue[] for authenticated team members; POST `/api/venues` and PUT `/api/venues/:id` are admin-only. Updates require revision. Venue = `{id,revision,name,address,latitude:number|null,longitude:number|null,coordinateSystem:'wgs84'|'gcj02',note,status:'active'|'archived'}`. Latitude [-90,90], longitude [-180,180], both finite numbers or both null. New records without coordinateSystem retain the legacy wgs84 default. Existing gcj02 records reject coordinate changes without an explicit coordinateSystem; metadata-only old requests remain compatible. No automatic coordinate conversion. No hard delete; archiving preserves history and prevents new match associations until restored.
- GET `/api/maps/config` is admin-only and returns `{provider:"tencent",enabled:boolean,key:string|null}` with no-store. The key is a public JS API browser identifier, never a signing SK or server secret. Missing runtime configuration disables the map. There is no mutation route.
- Match fields additionally accept `durationMinutes:number|null` (integer 1–1440), `notice:string` (plain text, at most 10000 characters) and `venueId:number|null`. The server creates `venueSnapshot:{name,address,latitude,longitude,coordinateSystem}|null` at association. Client-forged snapshot values are never trusted. Old snapshots missing coordinateSystem return wgs84 without rewriting their stored JSON. Same-venue edits retain the original snapshot; venue profile changes do not rewrite old matches. Legacy duration and venue remain null, notice empty, existing date/kickoff/location preserved. Wall-clock date and optional kickoff are not silently converted to UTC.
- PUT `/api/matches/:id/rsvp` with `response:null` removes the caller's own reply, restoring unanswered. As with other RSVP writes, only published matches allow it. Repeated changes remain one reply per player/match, not an accumulated click count.
- PUT `/api/matches/:id/photos` (admin) accepts `{revision,photos:[{id?:string,data?:string,caption?:string}],coverIndex:number|null}` and returns Match. Array order is display order; omit id for a new photo and supply canonical base64 image data. Existing IDs must belong to this match and may omit data. Caption is plain text up to 200 characters. `coverIndex:null` means no cover. Omitted coverIndex preserves the current cover if still present, otherwise uses the first image. The operation atomically replaces the gallery and increments the shared match revision; stale revisions return 409 without changing photos or match data.
- Maximum 10 photos, 2 MiB decoded bytes each, 16 MiB total. Static PNG/JPEG/WebP/GIF only, maximum 16 million pixels and 16384 per dimension. External URLs, SVG, animated containers, malformed encodings and undecodable data are rejected. The public upload route performs bounded full decoding before the store transaction; no remote image fetching occurs. Existing avatar compatibility is unchanged.
- Detail Match includes `photos:[{id,url,caption,byteSize}],coverPhotoId,coverPhotoUrl,photoCount`. List summaries omit photos and tacticSnapshots, retaining only cover metadata and normal match fields.
- GET `/api/matches/:id/photos/:photoId` returns raster bytes with derived Content-Type, `private, no-store`, `nosniff` and same-origin resource policy. Requires same-team login and visibility of the match; player access to draft photos and cross-team IDs returns 404. URLs are generated by the server, not client-defined. Photo bytes live in SQLite BLOBs and are included in the normal consistent backup.

Match notices are displayed content, not assent records. Neither uploading terms nor registering creates a legal-signature or waiver event in this API.

- POST `/api/auth/login` `{username,password}` -> session below
- GET `/api/auth/me` -> `{user:{id,username,role:'admin'|'player',playerId:string|null,teamId:number},team:{id,name,crest,revision}}`; 401 logged out
- POST `/api/auth/logout` `{}` -> 204
- PUT `/api/auth/password` `{currentPassword,newPassword}` -> 204, sessions revoked (login again)
- GET `/api/team` -> `{id:number,name:string,crest:string|null,revision:number}` (authenticated team members)
- PUT `/api/team` `{revision:number,name?:string,crest?:string|null}` -> Team (admin only, own team). Name is trimmed, nonempty and at most 200 characters. Crest accepts canonical base64 data URLs for image/png, image/jpeg, image/webp or image/gif, with matching raster file signatures and at most 2 MiB decoded bytes. External URLs, SVG, malformed encoding and mismatched signatures are rejected. The request limit is 3 MiB. Set crest to null to remove it. Revision is mandatory (428 missing/invalid, 409 stale). Login and auth/me return the complete current team object.
- GET `/api/players` -> Player[]
- POST `/api/players` Player fields -> Player (admin)
- PUT `/api/players/:id` partial Player fields plus `revision` -> Player (admin)
- POST `/api/players/:id/account` `{username,password}` -> `{id,username,role,playerId,teamId}` (admin; creates player login)
- PUT `/api/players/:id/password` `{newPassword}` -> 204 (admin; resets password, revokes sessions)
  Player = `{id:string,revision:number,name,number:number|null,positions:string[],preferredFoot:string,status:'active'|'inactive',note:string,avatar:string|null,hasAccount:boolean}`. Existing legacy string IDs preserved. New IDs generated. No destructive player delete: archive via inactive. Tactical desk and club roster reconcile by stable ID. Club profile edits increment tactical desk edition, so stale desk saves return 409 instead of overwriting newer profiles. Archiving revokes player sessions.

- GET `/api/seasons` -> Season[]
- POST `/api/seasons` `{name,startDate,endDate}` -> Season (admin)
- PUT `/api/seasons/:id` same fields, partial, plus `revision` -> Season (admin)
  Season = `{id:number,revision:number,name,startDate:'YYYY-MM-DD',endDate:'YYYY-MM-DD'}`. Inclusive arbitrary date ranges; overlaps allowed. Match membership is explicit, never inferred from overlapping dates. Narrowing a range to exclude an assigned match returns 409.

- GET `/api/matches` -> Match summaries (no tacticSnapshots) (players see published/completed/cancelled only; admin also drafts)
- POST `/api/matches` Match editable fields -> Match (admin)
- GET `/api/matches/:id` -> Match
- PUT `/api/matches/:id` partial Match editable fields plus `revision` -> Match (admin)
- PUT `/api/matches/:id/rsvp` `{response:'yes'|'no'|'maybe'|null}` -> Match (own player only; published matches only)
- PUT `/api/matches/:id/roster` `{revision:number,roster:[{playerId:string,position:string,appeared:boolean|null,goals:number|null,assists:number|null}]}` -> Match (admin, full replacement)
  Match = `{id:number,revision:number,opponent:string,date:'YYYY-MM-DD',kickoff:string,location:string,status:'draft'|'published'|'completed'|'cancelled',homeScore:number|null,awayScore:number|null,analysis:string,tacticIds:number[],rsvps:[{playerId,response}],roster:[{playerId,position,appeared,goals,assists}]}`. Required create fields opponent/date; other defaults empty, draft, null, []. Editable fields also include competition:string (default ''), format:5|6|7|8|9|11|null, side:'home'|'away'|'neutral'|'unknown' (default unknown), and seasonId:number|null. An assigned season must belong to the same team and contain the match date. Old matches migrate with seasonId=null and side=unknown, not inferred values. Only completed matches count in statistics. RSVP never counts as appearance. Goals/assists must be null unless appeared=true. `kickoff` is optional local HH:mm string. Tactic IDs validated against team's tactics. Score accepts null unknown, and explicit 0. homeScore is our team score. Known goals and assists totals may not exceed a known homeScore; both score edits and roster edits validate this.

- GET `/api/statistics?year=2026` or `?seasonId=1` -> `{filter:{startDate,endDate,label},matches:number,matchesWithoutRoster:number,team:{matches:number,scoredMatches:number,wins:number,draws:number,losses:number,goalsFor:number|null,goalsAgainst:number|null,goalsForKnownMatches:number,goalsAgainstKnownMatches:number},players:[{playerId,name,appearances:number,unknownAppearances:number,unrecordedMatches:number,goals:number|null,assists:number|null,goalsKnownMatches:number,assistsKnownMatches:number}]}`. No filter defaults current calendar year. Only one filter allowed. Sums are sums of known records; null when no known record; coverage fields indicate completeness. Appearance counts require appeared=true. unknownAppearances counts explicit roster rows with appeared=null. matchesWithoutRoster counts completed matches with no roster rows. Each player’s unrecordedMatches counts completed matches without any roster row for that player, including matches with a partial roster. Missing rows are unrecorded, not confirmed nonappearances; an explicit appeared=false row is a confirmed nonappearance. All coverage counts use the same match scope: explicit seasonId for a season, or inclusive match-date range for a calendar year. Season ranges do not implicitly assign matches. All players retained in stats including inactive.

Legacy `/api/tactics`, `/api/coaching-desk`, `/api/tactic-collections`, tactic versions retain payload contract; reads authenticated, writes admin only. Legacy board resource belongs to original team; other team identities cannot access it. Club tables all team scoped.

### Tactical roster reconciliation

Desk PUT returns the canonical roster in persisted desk order, followed by active club-only profiles. Clients must adopt the canonical response when no newer local edit is pending. Saving a non-null desk archives player IDs present in the previous canonical roster and explicitly omitted from the new roster, including appended club-only profiles. Before the first board is created there is no previous canonical roster, so pre-existing club profiles are retained and appended. Creating or editing a club profile increments the existing desk edition; an older client that has not received the new roster cannot silently remove it. Archiving revokes sessions but preserves accounts and match history. Explicitly adding an archived ID back to a current-edition desk restores active membership. A null desk resets the board without archiving membership. Desk write, roster synchronization, and archive/session changes commit atomically.

### Concurrency and historical data

Player, Match and Season have integer revision fields starting at 1. Updating an existing record requires the revision obtained when the edit began; missing/invalid revisions return 428 and stale revisions return 409 without changes. Match metadata and the full roster replacement share one Match revision. Successful updates increment revisions atomically. Clients must preserve edits on conflict and explicitly reload/reconcile, not silently fetch a newer revision and retry old full objects. RSVP updates affect only the caller’s response and do not change Match revision. Legacy tactical edits increment Player revision when profile fields or active status actually change; board-only/no-op saves do not.

New or changed player avatars accept only validated PNG/JPEG/WebP/GIF base64 raster images up to 2 MiB decoded. An unchanged legacy avatar is retained without revalidation (including old 20 Mi-character images and local paths), so profile editing and archival remain compatible. HTTP tactical desk saves apply the same changed-value validation, additionally allowing safe same-origin local raster paths; external URLs, encoded/slashed-origin tricks, SVG and query/hash components are rejected. Startup migration preserves old values. Player request bodies retain the server maximum (25 MiB by default); partial edits avoid retransmitting unchanged images.

Team statistics use the same completed-match/team/season-membership-or-calendar-year scope as player statistics. scoredMatches counts matches with both scores known. Wins, draws and losses use only those matches. goalsFor and goalsAgainst sum known values independently and are null when no corresponding scores are known; their KnownMatches fields describe coverage. Missing score sides never become zero or determine an outcome.

Match tactic associations now retain independent immutable snapshots, so template editing, version pruning and deletion do not change match history. Deletion is blocked only for an anomalous legacy link lacking its snapshot.

### Opponent records

Statistics also returns `opponents: Array<{opponent:string,matches:number,scoredMatches:number,wins:number,draws:number,losses:number,goalsFor:number|null,goalsAgainst:number|null,goalsForKnownMatches:number,goalsAgainstKnownMatches:number}>`. Groups use opponent names trimmed at the ends (case and internal whitespace are not merged), only completed matches from the authenticated team explicitly assigned to the selected season, or dated in the selected calendar year. Fields use the same independent score coverage as the team summary; an entirely unknown score does not become a draw or a zero-goal record. Results sort by match count descending, then name. There is no separate opponent entity or fuzzy name matching.

### Match history snapshots

Match adds `tacticSnapshots: Array<{sourceTacticId:number,tactic:Tactic,capturedAt:number,captureSource:'association'|'migration'}>`. The complete current tactic is captured when first associated, independently of the template/version tables. Existing tacticIds and snapshots survive template deletion; normal match edits retain them. Explicitly removing an association and adding it again captures the then-current template (which must still exist).

Each roster row adds `playerSnapshot:{id:string,name:string,number:number|null,positions:string[]}`, `snapshotCapturedAt:number` and `snapshotSource:'roster'|'migration'`. The initial roster save captures these identity/display fields. Later edits to goals, appearance or current player profiles do not refresh existing snapshots. Explicit roster removal/re-add captures the new values. Clients submit only editable roster fields; supplied snapshot fields are ignored.

Older records had no snapshots. The additive migration captures the values available at migration time and labels them migration. This does not reconstruct the original historical state. Read-only history must display this provenance. Snapshot data follows the match's team/role visibility; clients must not load current templates or players as a replacement for saved historical values.

### Explicit seasons, seasonal squads and attendance

GET `/api/seasons/:id/roster` returns `{season:Season,roster:Array<{playerId:string,name:string,number:number|null,positions:string[]}>}`. PUT on the same route accepts `{revision:number,roster:Array<{playerId:string,number?:number|null}>}` and fully replaces the season squad. Only admins may write; all team members may read. It shares the Season revision with season date/name edits. Members must belong to that team. Existing seasonal identity/position fields remain fixed, while numbers may explicitly change. Removing a member does not erase historical match snapshots. First capture of a match roster uses the assigned seasonal identity/number where present, otherwise the current player; subsequent same-row saves never refresh that snapshot.

Match roster rows include editable `selection:'starter'|'bench'|'unknown'` (default unknown), independent of actual appeared and RSVP. A substitute can have appeared=true; selection never implies appearance.

Season statistics use only explicit match.seasonId; calendar-year statistics use only match dates. Old records retain seasonId=null and continue appearing in year statistics. `unassignedMatches` is the team's total published/completed matches without a season (not restricted to the current filter), so the UI can surface records needing assignment. A match date outside its assigned season returns 400. A season range edit excluding assigned matches returns 409. Cross-team season references return 404.

Statistics adds `registrationMatches:number`, counting published/completed matches in the selected season/year. Each player adds `registration:{yes:number,no:number,maybe:number,unanswered:number}`. Drafts and cancelled matches do not count; absent replies are unanswered, never no. `team.attendance:{confirmedAppearances:number,unknownAppearances:number,matchesWithoutRoster:number}` uses only completed matches and actual roster appearance records, never RSVP. Unknown appearances count explicit appeared=null rows; missing rows remain represented by existing unrecordedMatches and matchesWithoutRoster coverage.

### Snapshot response limits

Only GET `/api/matches/:id` includes complete tacticSnapshots. GET `/api/matches` omits them to avoid loading every historical board for a list; it retains tacticIds and normal match/roster fields. New associations are limited to 32 MiB total UTF-8 serialized tactic snapshots per match. Exceeding that returns 413 and rolls back the entire edit. This accommodates one previously valid 25 MiB tactic. Existing migration captures larger than the limit remain intact, and edits that add no new snapshot do not reject or truncate them.
