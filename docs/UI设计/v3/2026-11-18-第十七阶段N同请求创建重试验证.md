# 第十七阶段 N：真实同编号创建请求重试

## 场景与隔离

本批接续17M，但使用另一新匿名隔离库。阶段24释放专属IDE后才接管，未操作正式球队数据。本批验证：用户查询时首请求尚未落库、查询后原请求才完成，此时再重试原任务不会重复创建。

代理只对首次 `/api/tactics` POST暂存请求正文和所需转发头于内存，并断开客户端连接，暂不发往服务端。180秒内未释放则丢弃，不自动发送；转发另有15秒超时。日志仅包含方法、路径、状态、阶段及正文/请求编号SHA-256，不记录正文或凭据。没有伪造404或成功响应。

## 原生实际操作

1. 真实登录匿名管理员，在新建页输入“17N匿名同请求核对”，7人制空白战术，点击创建。客户端出现未知结果。
2. 实际点击核对：服务端真实返回404。只读数据库检查，此时确实没有新战术或收据。
3. 在180秒期限内明确释放代理持有的首次请求。等待真实上游201及只读数据库确认新增唯一战术/收据后，才继续UI重试。日志没有超时或转发失败事件。
4. 点击“使用原任务重试”，确认框明确同编号同内容；先点击取消，未新增POST，原payload及本地收据保持。
5. 再次打开重试确认并确定。请求实际再次发送，服务端返回201，页面自动进入已有的同一战术ID。数据库仍仅一套新战术、一条历史、一条创建收据。

请求状态201是当前接口的实际返回，不据此声称第二次新建了记录。是否重复由唯一收据和逐表审计验证。

## 完整证据与审计

- 日志顺序：首次POST暂存不转发 → 收据查询真实404 → 释放原POST得到201 → 确认重试POST得到201。
- 首次请求与重试请求的正文摘要完全一致，请求编号摘要也与本地原requestId相符。未生成新编号。
- 取消确认后的日志没有重试POST；本地payload及收据与404后快照完全一致。
- 最终恰好新增一条战术、一条历史和一条收据。收据归属符合匿名管理员，payload_hash按服务端规范重算一致。
- 导航ID对应该唯一收据；完整页面模型、画布、数据库与版本hash一致，历史画布一致；成功导航后本地创建收据数为零。
- 原战术、历史、收据及其余业务记录逐表保持，认证运行记录另行核验，正常退出后会话数为零。

审计脚本已实际运行通过。本地证据目录 `football-ui-v3-interaction/tactic-stage17n`：`before-release.json`、`after-release.json`、404和取消后本地状态、进入画布模型、脱敏请求日志、截图、`audit.mjs`、`audit.json`及`completed.json`。数据库、凭据清单、匿名payload原件仅本地保存，不提交Git。

## 收尾与限制

本批使用可控代理构造“首请求延迟提交”的特定时序，不代替所有网络故障、跨进程恢复、请求内容冲突、战术已删除或真机环境。未验证首次请求永不提交时的重试；不能从同编号成功幂等推导所有创建异常都自动恢复。
