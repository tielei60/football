# 虚构俱乐部完整验收

运行：`cd app && npx playwright test realistic-club-acceptance.spec.ts fresh-club-board.spec.ts`。

仅使用 fixtures.ts 创建的有所有权标记的临时 SQLite 库和独立端口 5175；不连接人工演练端口、浏览器或数据库。单 worker 串行；长场景超时 180 秒。所有姓名和账号均虚构。

## 长场景

1. 管理员通过界面创建“星河周末足球队（虚构演练）”及林远、周禾、陈川三名球员账号。档案号码均 99。
2. 2091-08-01 至 2092-07-31 跨年赛季，赛季名单号码分别 9、6、12。
3. 2091-12-28 与 2092-01-04 两场同赛季比赛：河岸联队、周末友谊杯、8 人制、中立场、关联赛前战术。
4. 三人逐个退出/登录，第一场分别参加、不参加、待定。报名后名单仍为空，球员不见管理员保存按钮。
5. 第一场 2:1：林远首发出场、2 球 0 助攻；周禾替补未出场；陈川原报名待定、替补实际出场、0 球 1 助攻。第二场已完赛，比分及实际出场数据均保持未知。
6. 赛季胜平负 1/0/0，覆盖 1/2，确认出场 2 人次。三态报名列各 1。2092 自然年仅第二场，覆盖 0/1，球队及林远进球为“未知”，未回复报名 1，不当成 0 球或“不参加”。
7. 后改档案姓名和号码、后改原战术模板，历史比赛仍显示旧姓名、赛季号码 9 和保存的战术内容。
8. 原战术板真实下载 JSON 并解析 board。
9. 离开战术板完成保存，停止页面活动，再用现有 CLI 将数据库备份到新临时目录并恢复到另一离线路径。完整性、外键、所有表逐行相同；不替换运行库。

业务操作通过 UI。API 仅读取所创建记录 ID、准备和后改战术模板；不宣称战术拖拽等操作都由该测试手工验收。离线恢复不等于生产部署/跨版本迁移验收。

## Fresh 球队回归

归档 fixture 原球员，新建 4 名无号码球员，并注入外来旧浏览器名单缓存。进入战术板仅显示真实 4 人和当前队名，没有旧品牌；导出文件名为本队；首次保存后人数不增加、号码仍为 null，返回再进入仍 4 人。

服务端 null desk 必须提供 initialPlayers；新前端不会把本地旧名单自动上传。旧非空服务器工作台保留；旧浏览器草稿保留于此前备份机制。未知号码在名单显示“—”、编辑为空，球场不生成号码 0；显式 0 仍是已知号码。历史 IndexedDB 名不改，显式预置导入功能保留。

## 安全与证据

`realistic-acceptance-backup.mjs` 只接受标记 Playwright 临时目录内的普通非符号链接源文件，并校验 realpath 一致/包含关系。备份恢复全在新临时目录，结束清理。比较采用 isDeepStrictEqual 后的布尔断言，失败不把密码哈希/会话等行值写入 AssertionError。

自测：`node --test tests/realistic-acceptance-backup.test.mjs`，覆盖恶意源符号链接拒绝、正常恢复、不泄露敏感行值的失败诊断。

成功运行将截图 `realistic-season-statistics.png`、`realistic-annual-unknown.png`、`realistic-historical-match.png`，以及 `realistic-board-export.json`、`realistic-backup-verification.txt` 写入现有 CI 上传目录 `app/test-results/visual-review`。不输出账号密码或会话凭据，不上传数据库。
