# 第十七阶段 M：创建成功但回执丢失后的原生核对

## 实际覆盖及方法

阶段23释放IDE后，新建独立匿名演练库，真实登录管理员，在新建战术页输入“17M匿名创建回执核对”，保留默认7人制空白战术，实际点击创建。

一次性本地代理完整转发该POST，等待上游201及响应读取完成后断开下游连接。没有伪造成功或404，没有修改页面状态。代理仅记录方法、路径、上游状态、是否丢弃响应，不记录凭据或正文。

页面实际显示“创建结果尚未确认”，名称、人数和阵型锁定；原创建按钮被核对按钮替代，无“使用原任务重试”入口。只读运行时确认 `pending=true`、`busy=false`、`canRetry=false`；点击禁用人数控件无变化。

点击“核对创建结果”，真实GET返回200，页面确认创建成功。随后实际点击“进入已创建战术”，成功导航到核对到的同一战术ID，完整画布加载成功。本地创建收据在成功导航后清除。

本批全程只有一次创建POST。不存在的创建按钮没有被“再次点击”；也未用调用控制器方法伪造重复创建验证。

## 收据与数据审计

- 未知状态下本地收据包含原requestId、完整payload及createdAt；payload与控制器持有的内容完全相同。此证据是在断响应后读取，不声称独立捕获了发请求前的瞬间快照。源码写入顺序仅为补充依据。
- 核对后本地payload及收据保持，createdId有效、unavailable=false、canRetry=false；导航ID与核对ID一致。
- SQLite恰好新增1条战术、1条历史和1条创建收据。收据requestId与本地一致、tactic_id对应唯一新增战术；user_id/team_id与匿名管理员归属一致，payload_hash按服务端规范排序及SHA-256重算一致。
- 导航后完整模型与数据库记录、版本hash一致；画布与原提交payload一致，历史画布与最终画布一致。
- 原战术、原历史、原收据和其他业务记录逐表与基线比较不变。最终会话数为0。
- 审计脚本实际运行通过。本地匿名请求编号和payload仅保留于专用证据目录，不写入Git报告。

证据目录：`football-ui-v3-interaction/tactic-stage17m`。含 `unknown.json`、`recovered.json`、`entered.json`、请求状态日志、对应截图、`audit.mjs`、`audit.json`、`completed.json`。数据库、凭据清单和运行截图不提交仓库。
