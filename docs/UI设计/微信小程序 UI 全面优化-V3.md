# 微信小程序 UI 视觉层级与用户体验全面优化（V3 俱乐部版 · 32 页逐页执行与验收）

> **适用项目**：柏林花园 FC 原生微信小程序 `miniprogram/`。  
> **文档性质**：交付给开发者 / AI 编码工具的**执行任务书与逐页验收清单**，不是实施完成报告。  
> **视觉基准**：`Berlin_FC_MiniProgram_UI_Design_v3.zip` 中的 v3 页面图、长图、状态图和设计规范。  
> **代码参考基线**：V3 设计包记录的提交 `1f2505bd2f2bd7729475d73573639584c80ab3d4`；开始执行时**必须重新检查当前工作分支**。  
> **本次目标**：把现有小程序全面升级为**有柏林花园 FC 气质、与队徽匹配、看起来像完整足球俱乐部产品**的界面，并逐一完成全部 32 个页面及公用组件的真实运行检查、优化和复核。

## 一、任务范围与不可妥协的要求

本次不是简单统一字号、换主题色或美化首页。必须以 **V3 俱乐部版为最终视觉方向**，按现有 32 个路由逐页核查：**原业务结构 → V3 视觉目标 → 实际运行 → 差异整改 → 交互回归 → 多屏适配 → 截图与记录 → 复查通过**。任一步未完成，不能标记该页“已完成”。

1. **覆盖全部页面**：以当前项目 `miniprogram/app.json` 的实际路由为准，V3 基线为 32 页；逐页核对数量、页面路径、角色分支、长内容和异常状态。实际分支若新增或删除路由，先列出差异，不能直接忽略或擅自新增产品功能。
2. **以 V3 重新设计展示层**：允许重新安排同一页面已有内容的展示顺序、主视觉和控件布局；不受旧版浅灰紫卡片布局限制；但不得擅自更改导航关系、业务字段、权限或数据语义。
3. **逐页实际修改**：每个路由都应有独立代码审查和视觉结果；无需修改的页面也必须经完整检查并说明“无需修改”的证据，不能以全局换色视作已完成。
4. **完整保留交互**：不得删除已有按钮/字段/说明/状态，不得更换接口、数据库、校验规则或请求参数，不得破坏已有并发保护、任务核对、会话清理和历史快照。
5. **不得额外增加需求**：不新增新闻、天气、比赛倒计时、财务、签到、公开注册、多球队切换、球员能力雷达、虚构出勤率或新的 AI/微信能力；V3 概念图的演示内容不等于系统已实现功能。
6. **不使用整屏图片代替界面**：球场、球衣与品牌装饰可用授权图片；队徽、真实日期、比分、状态、人数、按钮、表单和列表都必须是动态内容或原生组件。
7. **保留技术边界**：原生 `Page + WXML + WXSS + JavaScript + wx.*`；原有 REST 后端与权限边界不动；不新引入 UI 框架，不以 WebView 或 HTML 原型直接替换原生页面。
8. **未验证就不能称完成**：构建通过不等于页面通过，截图好看不等于业务通过；微信开发者工具和真机未执行的项目必须明确标“待验证”。

## 二、必须达到的品牌与视觉标准

### 2.1 柏林花园 FC 的视觉识别

- **球队身份必须明显**：首页、比赛、球员、数据和我的五个入口有各自的视觉主题；队徽、球场、球衣、紫蓝曲线与足球元素形成统一的“俱乐部产品”观感，而不只是普通管理系统换成紫色。
- **有主题但不过度铺图**：首页采用球场氛围、比赛采用赛事对阵、球员采用球衣纹理、数据采用紫色标题区与白色战绩卡、我的采用会员身份卡；管理页保持轻量表单与统一品牌细节。
- **深浅搭配**：深紫用于焦点和关键操作；白色承担阅读区；浅紫用于衬底；冰蓝只作辅助高光。禁止大面积紫色压住正文、用花哨渐变覆盖所有按钮，或把所有页面做成同一张卡片。
- **队徽必须准确**：保留队徽盾形、横幅、文字比例和真实颜色；无高清矢量时使用 V3 中 256×256 PNG 的合理尺寸，避免拉伸和无依据锐化。队徽出错时提供回退标识。
- **素材真实性**：`club-atmosphere.jpg`、`jersey-detail.jpg` 与 `demo-avatar.jpg` 是从生成概念图裁切的视觉素材，非真实比赛、球场、球衣或球员证据；上线前审核授权，低清细节不适合无限放大。没有真实照片时应使用队徽、渐变和首字占位，不伪造球队合影或同一人头像。

### 2.3 字体、信息层级与字段

1. 每页先确认一级信息：下一场、对阵、球员身份、当期战绩、当前任务等。一级信息有显著字号/位置差异，不靠全页加粗。
2. 字段名称弱于字段值；“日期 / 开球时间 / 地点 / 赛季 / 比分 / 姓名 / 号码”显示完整，并保持语义标签与数值视觉对应。
3. 对长队名、长对手、长场地名、多位置、两行状态和错误说明，允许自然换行；不得为整齐截断关键业务信息。
4. 金额不属于本小程序的既有核心数据，禁止沿用原通用文档中的“金额卡片”等无关组件模板。
5. 重要数字、比分和排行按统一数字字形对齐；没有记录的值使用 `—`，零只表示有确认记录的 0。
6. 状态同时采用文字与样式；“待定”“未回应”“请假”“已报名”“未出场”“出场待确认”等不得合并成一个绿色成功标签。
7. 图标使用 V3 同一线性风格与队徽紫；图标大小/描边一致；不能使用含义不明的 emoji 代替主导航图标。

### 2.4 页面结构、组件与性能

- 五条 Tab 的**显示文案**统一：**首页 / 比赛 / 球员 / 数据 / 我的**；保留现有 `pages/home/index` 等五条路由，不增设第六入口，也不改变既有页面跳转关系。
- 使用 V3 的赛事焦点卡、普通比赛卡、球员行、会员卡、战绩卡、通用表单、底部报名栏。可参考 `native/components/club-match-card`、`club-player-row`、`club-response-bar`，**先核对当前项目结构与事件再整合**，不能直接覆盖整页代码。
- `page-state`、`loading-skeleton`、`business-dialog`、`business-picker`、`invite-sheet` 及原生 `map/canvas` 必须逐项复核。选择弹层和日历/时间面板的视觉统一，不改变已有触发、取消、确认及回填规则。
- 图片只用于可裁切背景和头像。比分、报名状态、分组数量、按钮文案等始终基于真实返回值渲染，不能以静态海报或演示数值占位。
- 不重写请求层；保留隐藏页面清理、会话切换、重复点击拦截、失败核对、版本冲突和图片失败回退。背景/阴影/渐变以不造成滑动卡顿和低端设备渲染异常为前提。

### 3.1 每个页面的最低场景覆盖

- **正常**：当前业务能完整走通，首屏和长图对照 V3。
- **加载、空和失败**：至少分别验证“加载中 / 真空列表或无内容 / 请求失败”，不能把失败渲染成“暂无数据”。
- **权限**：对存在权限差异的页面分别验证球员、普通管理员和系统管理员（按适用范围）。
- **内容边界**：超长中文/英文名字、缺少头像与队徽、长备注、数字 0、未知 `—`、图片失败、超过一屏列表。
- **操作中及异常**：请求中禁用重复提交；后端成功后才提示成功；冲突和结果未知必须按页面已有流程恢复。
- **屏幕适配**：每页至少 320、375、430 CSS px 三档实际渲染；页面含原生键盘、地图、画布、相册、选择器时，另验微信开发者工具以及可获得的 iOS/Android 真机。**三档 HTML 原型检查不等于原生小程序适配通过。**

### 3.2 检查顺序（每一页都要重复）

1. 读取当前页面 `.wxml/.wxss/.js/.json`、用到的组件和关联接口映射，列出全部显示字段、事件、权限及状态。
2. 打开 V3 对应 `design/screens/XX-key.png` 和 `XX-key-full.png`；存在状态图时也打开 `design/states`。在代码中明确“保留 / 调整 / 不适用”。
3. 使用隔离测试数据或既有模拟测试让页面运行，**记录改造前**首屏、长图、关键状态与业务入口。
4. 仅修改展示结构、必要样式和界面绑定适配，不动业务含义与接口；逐项核对字段和事件未丢失。
5. 重新运行页面，**记录改造后**首屏、长图、权限与异常状态；分别在 320/375/430 三档检查。
6. 点击本页所有可用控件，检查确认/取消/失败/返回/刷新；对数据写入流程在隔离环境验证前后状态及网络请求结果。
7. 执行该页相关自动化检查，进行至少一次人工视觉复查和一次代码复查；修正后重复步骤 5–7，直至通过。
8. 在逐页验收台账登记结果，附可打开的证据路径。任何未实际运行的页面必须标“未验证”，**不能**填写“通过”。

## 四、32 个页面的逐页检查与优化要求

> 每个页面均须执行第三章的 **C01–C16**，以下是该页特有的**额外硬检查**。`字段`/`事件`/`状态`来源于 V3 的 `spec/page-specifications.json`，需要与执行时实际分支再次核对；文档中的代码事件名只是参考，不授权重写事件链。  
> 页面图参考：V3 ZIP 根目录内的 `design/screens/`。缺少专门状态图的页面，**需要从实际小程序制作对应状态截图，不能跳过状态检查**。

### 01｜首页（`pages/home/index`）
**权限**：成员可查看，管理操作按权限。**V3 目标布局**：紫色球场主题首屏 → 下一场白色对阵卡 → 四个快捷入口 → 近期赛果 → 自然年数据。
**设计图**：`design/screens/01-home.png`、`design/screens/01-home-full.png`。  
**重点状态图**：`design/states/04-home-no-next-player.png`, `design/states/05-home-loading-player.png`。
**现有字段必须逐项核对**：球队名称/队徽；角色标签；已确认在队人数；未确认人数；本年完赛/胜场；下一场赛事/人数制/对手/日期周几/时间/地点；参加/待定/请假与本人回应；最近赛果。
**原有事件必须保持**：schedule→赛程；openMatch→比赛详情。
**必须覆盖的状态**：空下一场；无赛果；加载；失败；队徽失效。
**本页逐项检查与实际优化：**
- [ ] 逐项核查队徽、球队名称、球衣/球场氛围图、紫色遮罩、首页标题和微信胶囊的距离；背景可以裁切，动态文本与按钮不得烘焙进图片。
- [ ] 下一场比赛的赛事、对手、人数制、日期（含周几）、开球时间、地点和我方/对方标识必须完整，优先展示对阵与报名入口；重要字段超长时允许换行。
- [ ] “比赛、球员、数据、战术”快捷入口应与代码已有入口对应，不增加新闻、天气、倒计时或新的业务功能。

## 八、实施阶段、复查与交付方式

**阶段 A：建立基线（必须先做）**  
查看执行分支的 `app.json` 与全部页面、共用组件和样式；生成准确路由清单，与 V3 的 32 页映射对照。保留修改前截图，确认每页全部字段/事件/权限/特殊状态。发现 V3 页面与当前功能不符，先记录差异，不擅自删减。

**阶段 B：建立品牌基础**  
在原生项目中合并 V3 令牌、图标、导航样式、卡片、按钮、表单、弹层及素材回退；检查全局影响。完成五个 Tab、首页和比赛详情的实际渲染对照，确认视觉方向正确后再铺开。此阶段完成不意味着其他页面完成。

**阶段 C：逐页实施（32 页逐页关闭）**  
按照“首页、比赛、球员、数据、我的 → 登录与详情 → 管理表单 → 名单和媒体 → 战术与导出 → 微信/AI/系统账号”的顺序，逐个页面执行第三、四章要求，修改、运行、记录、复查。不允许一次批量替换所有页面后笼统判定完成。

**阶段 D：公共变更复归（再次全量 32 页）**  
所有页面完成后，对 App 全局样式、各 Tab、所有共享组件和主题素材执行跨页面对照，复查已有改动是否影响早期通过的页面；逐页重新打开并核验最核心可见信息、操作、异常状态与截图。

**阶段 E：回归和交付审查**  
执行现有自动化和隔离数据流程，在微信开发者工具中逐页实测，能用真机时补充 iOS/Android；必要时再修复并复测。提交代码审查与检查记录，保留未验证事项，保证任何一次样式修改后都能按此清单重新回归。

### 必须提交的结果（不可只写“已优化”）

1. **已实际修改的源码**：原生页面 WXML/WXSS/必要界面 JS 与共享样式/组件；不能只提交 V3 设计图或文档。
2. **32 份页面检查记录**：每页独立列出问题、修复、实测、状态与屏宽适配、遗留问题、最终结论。
3. **每页改造前后截图**：首屏及长图 + 适用异常状态；一切关键数据与业务控件在图片中可辨识。
4. **共享组件与全链路回归记录**：明确命令、通过/失败、失败修复、重跑结果及不同身份路径。
5. **代码复核结果**：确认无未授权接口变更、数据结构变更、业务规则改变或新增需求；列出已知未验证的微信平台能力。
6. **提交与对照**：在独立开发分支提交可追溯变更，按项目要求推送/合并；若没有仓库写权限只交付补丁与检查记录，不声称已推送。

### 最终判定

只有当 **32 个原生页面全部经过实际查看、按 V3 改造或证明无需修改、逐页回归与复查、所有适用状态和权限已确认、共用组件与相关流程无回归**，且剩余事项标注清楚时，才能交付该轮 UI 优化。若缺少微信真机条件，最终应准确写为“已完成开发者工具/模拟环境验收，待 iOS/Android 真机验收”，不能写“全平台已通过”。
