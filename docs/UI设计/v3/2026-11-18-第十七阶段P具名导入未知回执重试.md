# 第十七阶段 P：具名导入未知回执重试

## 目标与边界

本阶段验证 17O 具名导入改动后的未知结果保护。使用全新匿名隔离库、专属交互工程及真实微信开发工具操作，不访问原工程或正式数据库，不发送文件到聊天，不使用接口直接导入冒充 UI，不修改产品代码。

复用 17O 匿名文件内容（文件内仍为 17O 标签），每份包含一套战术和一个历史版本。文件由系统选择器实际选中；未 mock 文件回调，未调用页面方法或修改页面数据制造结果。

## 首批：自动补发观察，不算人工重试

首批代理等真实上游 201 的完整响应读取结束后，仅丢弃首次下游回执。开发工具网络层随后自动补发了同一请求，服务端返回 200、`verified/repeated`、新增 0，页面直接显示此前导入已确认。

因此，这批只能证明自动补发下的去重，**没有进入待核对状态，不计为人工重试完成**。保存了请求全文 SHA-256、状态、同一战术 ID、三个业务表各增一条、退出后会话为 0 的可复跑审计；未把这批宣称为完整模型审计。

## 第二批：实际待核对与人工重试闭环

另建独立匿名库。故障窗口内，代理始终等待真实上游提交并读完回执，再断开下游连接，不伪造接口状态。

1. 实际选择具名文件，副本选项默认未选；确认导入。
2. 首次上游 201 新增一套。网络层自动补发获得上游 200、已验证重复；两次回执都被断开。
3. 页面实际进入 `pending=true / busy=false`，显示“导入结果未确认”。选择文件与独立副本选项均禁用。实际点击禁用入口未打开选择器或改变选项。
4. 只读记录本地守卫仍保留原导入名称。点击“核对并重试导入”，确认框明确继续原任务；先取消，代理仍只有前两次 POST，业务数据无变化。
5. 解除仅本批回执故障后，再次实际点击并确认重试。第三个 POST 返回真实 200、`receiptVerification=verified`、`repeated=true`、`importedCount=0`，战术 ID 与首次相同。
6. 页面显示“此前导入已确认，本次未重复新增战术”，清空文件选择与 pending，本地导入守卫清除。
7. 实际进入导入后的战术画布，读取完整模型及版本，与数据库和源文件逐字段对账。

本批真实 POST 共 **3 次**：首次请求、故障期自动补发、解除故障后的人工确认重试。不是两次，也不把自动补发计作人工操作。

## 数据审计

可重跑审计已通过：

- 三次请求全文哈希完全一致，状态 `[201, 200, 200]`，丢弃回执标志 `[true, true, false]`。
- 待核对、取消重试、最终成功三份完整业务表快照一致，证明首次提交后未重复写入。
- 相比基线，战术、历史、导入收据各恰好新增一条。
- 新增战术完整模型、画布、标题、标签、收藏、阵型、缩略图与匿名文件对应；页面版本与数据库规范化模型哈希一致。
- 历史画布、备注、时间与源文件对应；收据原名称、战术 ID、规范化内容哈希一致。
- 全部原记录及其余业务表保持不变。会话、登录尝试、自增序列不作为业务快照比较项，会话另核为 0。

## 安全收尾与证据

两批均正常 UI 退出回登录页，隔离会话为 0；配置先核对本批归属，再逐字节恢复原备份；专属窗口关闭，临时服务和代理停止，两个已记录 PID 均不存在。

本地证据（不加入 Git）：

- `football-ui-v3-interaction/tactic-stage17p/`：首批请求、有限范围审计、配置恢复记录。
- `football-ui-v3-interaction/tactic-stage17p-retry/`：`pending.png`、`success.png`、页面与守卫只读记录、请求日志、取消时日志、业务快照、完整模型、`audit.mjs` / `audit.json`、收尾记录。

日志不保存凭据或请求正文，仅记录请求哈希、路径、状态及白名单结果字段。截图中禁用按钮和紧凑副本勾选与现有 V3 页面层级保持一致。

## 未覆盖项

本批不等于重启后失去内存任务的恢复阻塞验证，也不涵盖旧收据原生提示、未知后跨账号/跨进程恢复、独立副本未知重试、真机文件选择或系统另存。上述边界继续保留在清单，不宣称全部导入异常已覆盖。
