# UI V3 阶段50：微信邀请交错请求核验

## 结论
本轮未发现新的确定业务缺陷，未修改产品实现。依据独立代码审查补齐并发和交换等待期间的实际HTTP证据，不凭推测新增规则。

## 新增4项隔离验证
使用临时SQLite、本机真实HTTP服务及模拟微信响应，所有姓名、身份和凭据均为测试值，没有真实微信网络调用。

1. 同一创建编号同时提交两次，返回201与200各一次，相同邀请ID，仅首次返回凭据，数据库只有1条；另一个编号创建同球员活动邀请返回409。
2. 暂停甲身份交换，乙先完成认领，再释放甲。甲409，邀请归属、确认码及版本保持乙的记录，没有绑定。
3. 同一微信身份先认领两个球员的邀请，再同时发批准请求：恰好一个200、另一个409。只有一个账号及绑定；失败邀请仍claimed且版本不变。重复批准409、不增绑定；随后登录所得用户ID确为胜出绑定账号。
4. 暂停身份交换，在隔离库让邀请到期，再释放交换结果。首次认领409，不写认领身份、不增版本、不创建账号、绑定或会话。

完整后端249/249通过，`git diff --check`通过。此前顺序竞争、跨队权限、归档/解绑ABA及重放已有测试，本轮补的是请求交错而非宣称这些功能此前不存在。

## 准确边界
这是单服务进程上重叠HTTP请求及受控异步交换的验证；同步SQLite事务仍串行，不等于多进程、多服务器或高负载压力测试。真实微信扫码、平台一次性code行为、真实网络及手机环境未验证。没有调用真实微信、配置密钥、产生费用或触碰Mac正式数据。

本轮仅测试及文档变化，未重跑小程序完整检查；最近阶段49为1323通过、27项布局受云端socket权限阻碍。阶段41–48原生after及这些布局检查仍待完成。
