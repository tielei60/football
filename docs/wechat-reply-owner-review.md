# 报名页面加载身份门禁

## 先失败再修复的匿名证据

原实现的匿名 VM：A 身份成功加载已发布比赛，保持同一页面实例后切为 B，再点击旧页面参加按钮，实际发出 1 次 PUT；新增断言要求 0 次，首次运行 11 项中 10 过、1 失败。这不是实际账号或服务操作。服务端仍按当前登录者绑定球员处理，并非替 A 写报名；问题是旧页面操作被作为新身份提交。

## 最小修正

仅比赛详情页在成功刷新、最终代次/可见性/身份检查通过后，记录私有加载 owner。每次刷新开始清除此资格；提交报名前必须与当前会话一致。未完成或失败刷新不能授予提交资格，隐藏/卸载沿原门禁。B 重新成功加载后可正常报名，不永久封锁。

不修改后端、报名协议、页面模板、配置或权限规则。关闭比赛仍由服务器拒绝；已知 409 保留原提示和显式刷新，未知结果仍先读取核对，不自动重发写入。

## 验证范围

报名串行测试原 4 项保留，新增 13 项，共 17 项：A→B 旧页零 PUT、B 重载恢复；初次/失败刷新；隐藏/卸载/换账号/较新读取抢先；取消/完赛 409 无乐观改回应及显式刷新禁报名；0/500 未知结果读到关闭状态不重发。

另外 member-context 的已加载页面夹具仅补私有 owner 前置，保留原全部断言；pages-flow 正常刷新路径无须修改。三文件联合测试 72 项通过。测试是匿名 VM 及 API 替身，不等于真实微信跨账号 UI 或服务端并发全链路验收。截止时间没有新增规则，现有报名开放条件仍为已发布状态。

## 后端状态组合自动回归

`server/club.test.mjs` 共 27 项通过。其中取消、完赛与三种报名回应的 6 种组合，通过实际 HTTP 请求验证均返回 409，数据与统计输入深度比较不变。这是自动 HTTP 检查，不代表 6 种组合全部做过真实 UI 操作。全原生 645 项、官方模板 139 次渲染及 Web 构建通过；A → B 的身份切换仅在匿名 VM 中验证，没有注入或操作真实账号。

## 匿名球员旧页面实测

将既有全匿名来源复制并迁移到另一独立副本，既有账号字段不变，清除复制过来的旧会话、不复用旧会话。通过官方输入正常登录既有虚构球员账号，没有新增账号或修改密码。初始虚构比赛 1 为 published、revision=1、NULL 比分，球员回应为 yes；这些初始数据是预置，不是 UI 创建。

1. 球员实际加载已发布旧页面后，后台通过正常 CAS 将比赛取消至 revision=2。旧页仅点击一次“请假”，页面提示仅已发布比赛可报名，仍保留 yes。独立核验 32 张表与取消后的基线完全相同。实际返回赛程后，从已结束卡片重入，显示已取消且无报名按钮。
2. 后台通过正常 CAS 重新发布至 revision=3，球员实际重入已发布页面；随后后台设为完赛、revision=4，并保留 NULL 比分。旧页仅点击一次“待定”，同样被拒绝。32 张表及全部统计输入与完赛后基线完全相同，来源库未改变。

以上两次是真实 UI 操作配合后台业务层状态变更，不是第二管理员前端操作，也不等同于 6 种组合全部实际点击通过。最终实际返回赛程，从已结束卡片重入，显示已完赛、比分为 —:—、无报名按钮；随后正常退出至 375 宽度空登录页，会话数为 0。

后台通过正常业务层 CAS 恢复为 published、revision=5。比赛完整行相对预置基线仅 revision 从 1 增至 5，yes 回应及 NULL 比分保持；其余 31 张表与预置基线完全相同，来源库全部表不变。这是后台数据恢复，不是 UI 完成恢复状态，也未回退版本。配置经双 SHA 守卫恢复原字节，本轮服务执行会话 exit 0、对应端口无监听，收尾完成。

上述结论限于两项匿名球员实际旧页操作、页面重入及独立数据核验，不扩大为实际跨账号切换、全部状态组合的真实 UI 或真机验收。
