# UI V3 阶段49：微信邀请成员确认门禁

## 已证实的缺口
V3邀请页和前端已阻止未确认成员发起邀请，但服务端仅检查active。隔离HTTP调用先保存 `status=active、membershipConfirmed=false`，再创建邀请，修前返回201，预期409。确认状态与active本来独立，不能简单把未确认视为停用账号。

## 最小修复和授权边界
- 服务端新建邀请、首次认领、管理员批准时核对成员确认状态；明确未确认返回409。
- 已创建请求的同编号重放仍只恢复元数据，不返回邀请凭据。已认领的同微信身份重放仍能恢复确认码和状态，不重复认领或发会话；其他身份不能恢复。
- 查询、撤销及既有绑定登录保持原规则。取消确认不擅自解绑、不撤销既有账号会话；归档停用仍执行原有撤权。
- 主应用旧数据库迁移默认已确认；独立旧表无确认列时保持原有已确认语义。原有迁移、历史名单和统计不变测试继续通过。

## 实际验证
新增5项测试采用临时SQLite、真实本机HTTP路由和模拟微信平台响应，未调用真实微信、未使用真实凭据：
1. active且未确认成员不能创建邀请（修前201→修后409）。
2. pending邀请的成员取消确认后不能首次认领，仍可查询撤销。
3. claimed邀请取消确认后不能批准；原认领者可恢复相同确认码，外人不能；版本与绑定数量不变。
4. 既有绑定及会话不因确认元数据而失效；旧创建重放不泄露凭据；重新确认后可正常邀请。
5. 已认领邀请到期后批准409，路由查询按既有规则落库expired并增一次版本；后续本人重放仅恢复到期元数据，不再修改邀请，不建账号、绑定或会话，其他身份不能恢复。
