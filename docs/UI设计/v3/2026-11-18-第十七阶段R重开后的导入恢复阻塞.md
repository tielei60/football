# 第十七阶段 R：重开后的导入恢复阻塞

## 验证范围

在新匿名隔离库中实际制造已提交但回执丢失的导入，再正常关闭专属开发工具窗口并重开，不清除本地存储。验证内存任务丢失后仍阻止重复导入，核对列表及解除提醒的取消、确认行为。

未改产品代码，未访问原工程或正式数据库；文件选择及所有确认均为真实 UI 操作。只读读取页面状态与存储证据，不调用页面方法或注入 pending。

## 真实操作

1. 使用匿名账号登录，系统文件选择器实际选择匿名具名文件，确认导入。
2. 代理等待真实上游 201 完整提交后断回执；网络层自动补发得到 200 已验证重复，也断回执。页面进入 pending，持久化守卫存在。
3. 正常关闭窗口后立即重开，第一次返回 `reuse`，随后运行时查询表明窗口已无 runtime。此结果**不作为完成重开证据**。
4. 再次官方打开项目返回 `newopen`。进入导入页只读观察：`pending=false`、`recoveryBlocked=true`、文件名为空，本地守卫名称和创建时间与关闭前完全一致。
5. 页面明确提示原任务内容已不在内存，选择文件禁用。实际点击禁用入口没有打开选择器。
6. 点击“查看战术列表”，实际看到已导入的匿名战术；返回导入页。
7. 点击解除限制，确认框说明解除提醒不会撤销或删除已导入战术。先取消：恢复阻塞和原守卫保持，完整业务数据不变。
8. 再次点击并确认“已核对”：守卫清除，恢复阻塞解除，文件选择入口恢复。页面明确“核对提醒已解除，已有战术未作任何改动”。未重新选择或导入文件。

上述重开只针对专属项目窗口，不宣称重启整个微信开发工具应用或用户电脑。初次 `reuse` 与后续实际 `newopen` 已分别留证据。

## 数据核验

- 全程只有关闭窗口之前的两次导入 POST：201 首次提交、200 网络自动补发，两次请求全文哈希一致；后续查看列表、取消、确认解除均未增加导入请求。
- 原任务关闭前、重开后、解除取消后的守卫内容精确一致；确认解除后守卫为空。
- pending、取消、解除确认、最终退出四份完整业务快照一致：解除操作没有新增、修改或删除任何战术、历史或收据。
- 与最初基线相比，最初导入仅新增一套战术、一条历史、一条收据，其他原记录和业务表保持不变。
- 会话和登录尝试、自增序列不纳入业务快照比较；最终会话另核为 0。

可复跑 `audit.mjs` 已全部通过。本批重点是恢复守卫与零业务变更；完整文件内容和模型哈希导入质量由前面 17O／17P／17Q 批次覆盖，不重复宣称本批已审所有导入格式。
