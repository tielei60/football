# 球员归属状态确认元数据

`membershipConfirmed` 是球员响应中的布尔值，与操作字段 `status` 分开：`false` 表示来源资料中的当前成员归属尚未确认，不能据 `active` 技术状态宣称正在队，也不能据 `inactive` 宣称真实离队。

## 兼容与编辑

- SQLite 新增 `club_players.membership_confirmed`，严格0/1，旧资料默认1，保留既有业务语义；迁移在事务内、可重复执行。
- 球员 GET、列表与保存响应均返回布尔 `membershipConfirmed`。历史来源展示副本应显式设置false，不反写来源库。
- 现有管理员创建/编辑接口接受此字段，必须是真正布尔；编辑继续携带 `revision`，旧版本409，同队校验不变。缺省编辑保留原值，修改备注或归档/启用不会自动确认归属。
- 新建默认true沿用管理员直接登记的既有语义；来源导入者必须显式false。只有管理员可以确认，球员不能提交自身声明替代管理员权限。
- 不新增权限，也不放松原有基于 `status` 的操作规则。保存 `inactive` 资料时，即使本次仅改确认元数据，仍执行既有归档撤权：递增微信授权代次、撤销有效绑定及待处理邀请、清除对应账号会话。未知状态不能绕过此规则。报名、名单、统计与历史快照的既有口径保持。此字段不是身份核验、授权证明或新的权限凭据。

前端应对false显示“状态未确认”，以独立筛选/提示避免误显示“在队”或“已归档”。元数据本身不会自动修正任何旧来源事实，也不代表已核验真实成员归属。

## 自动验证与边界

6项匿名专项覆盖：旧schema迁移与重开、默认值、缺省保留、严格类型、同队CAS、写入失败原子回滚、HTTP管理员写与玩家只读、确认变更不影响历史快照及统计，以及 inactive 元数据保存仍执行既有会话和绑定撤销。测试使用独立临时库，无真实名单或凭据。实际界面与干净展示副本的处理须另行核验，不用自动测试冒充已展示。
