# 柏林花园历史名单本机演练

## 事实与模拟的分界

- **历史来源**：20人的来源编号、姓名和位置来自项目中相互核对的前后端字面量；这不是逐人确认现实情况。
- **保持未知**：球衣号码、头像、惯用脚、出生日期、健康和当前成员状态没有可靠来源，不按默认值补造成事实。
- **仅演练变化**：新副本中的临时在队状态、两个随机测试账号，以及操作者随后新建的比赛、报名、名单和统计，全部属于本机模拟，不表示本人在队、注册授权、真实比赛或成绩。

不要把此副本上传、导入生产、截图公开或当作真实俱乐部运行资料。真实名单不会复制进测试代码或提交到Git。

## 如何启动

安装项目依赖，使用符合项目要求的Node.js，在仓库根目录执行：

```sh
node scripts/start-berlin-rehearsal.mjs
```

不接受路径、端口、账号或其他参数。每次运行：

1. 调用安全来源生成器，新建私有 `football-berlin-validation-*` 临时目录及 `validation.sqlite`。这不是备份、恢复或复用此前生成的某一份资料库。
2. 使用SQLite backup API复制到独占新目标 `rehearsal.sqlite`，核对源库前后摘要；不直接拼接或复制活动数据库文件。
3. 原来源库仍保留隔离 `inactive` 状态和原字段。只在演练副本中临时启用20人、追加醒目模拟说明、创建2个随机密码的虚构球员账号；不预置比赛或统计。
4. 启动仅监听 `127.0.0.1` 的随机端口服务，微信和AI均关闭，无外部地图调用。不会修改小程序配置、原有数据库或其他服务。

终端只打印本机地址和私有账号清单路径，不打印姓名或密码。目录权限0700，源库、副本及清单0600。管理员使用本次新源库生成的随机密码；两个球员账号的用户名和密码均随机，账号关联只为演练，不是替真实本人注册的正式账号。

本机清单 `rehearsal-private-manifest.json` 包含地址、来源摘要、管理员和两名测试账号。只在本机查看，不上传、不贴进聊天或日志，不提交到仓库。操作者需要在小程序中自行选择该本机测试地址，结束后恢复原配置；回环地址不代表手机真机可访问。

## 可复现的操作矩阵

此表是本地复现步骤与验收标准，不是所有步骤已实测通过的声明。

| 步骤 | 操作 | 核验标准 |
| --- | --- | --- |
| 管理员进入 | 使用本次清单里的管理员账号登录 | 队名含本机模拟标记，可见20人；号码/头像等未知字段不被自动补值 |
| 球员身份 | 分别使用两组随机球员账号登录 | 对应各自来源编号；不能调用管理写入接口，不能修改其他球员资料 |
| 建立演练周期 | 管理员创建名称带“演练”的赛季，设置起止日期 | 周期保存后重新进入仍一致；不当作真实赛季 |
| 发布模拟比赛 | 管理员创建对手名带“演练”的比赛并发布 | 日期、时间、时长和须知保存一致；不填真实场地坐标或发起地图导航 |
| 报名状态 | 第一账号报名，第二账号待定；再将第一账号改为请假 | 各自当前状态、人数和管理员名单一致，不生成重复报名 |
| 名单与位置 | 管理员选择模拟出场球员和位置 | 保存后重开相同；未选者不因“在队”自动计为出场 |
| 数据登记 | 管理员录入明确虚构比分、进球与助攻 | 比赛、球员及赛季统计对应，未登记部分不被补造 |
| 修改及重复操作 | 返回修改一个模拟结果，重新进入并重复刷新 | 统计不重复累加，最新记录持久化；冲突应提示重新核对 |
| 权限复核 | 切换球员身份访问相同比赛 | 只能操作自己允许的报名状态；管理写入被服务端拒绝 |
| 关闭核验 | 停止服务后检查源库与副本 | 原来源库摘要不变；模拟数据只在副本中，未污染原有项目数据库 |

所有模拟比赛、报名和成绩只存在该副本；不要把演练截图当作球员事实。需要真实运营前必须另行核实成员现况、字段和个人资料使用范围。

## 停止、保留与失败处理

按 `Ctrl+C` 或 `SIGTERM` 停止本次服务，等待 `server.drained` 结束任务和SQLite资源收尾，不强制退出。正常停止保留本次源库和副本以供本地检查；系统临时目录可能被清理，不能当作长期备份。

启动失败只清理本次自己新建的目录，不删除其他验证库、演练库或生产库。手工清理前先停止服务并核对确切目录，不使用通配符批量删除。

## 匿名自动化验证

```sh
node --test app/tests/berlin-rehearsal.test.mjs
```

测试设计用匿名字面量替换真实来源，覆盖参数拒绝、源库与副本字段关系、临时状态说明、随机账号、空历史、权限与环境哨兵、两次启动互不复用、backup失败/监听失败清理，以及close回调报错仍等待drained后再返回。不会把20人的真实姓名写入测试库或测试输出。

2026-11-14 正式落盘后，上述6项匿名测试全部通过，0跳过。测试中生成的目录已清理，未启动长期真实名单服务。故障测试通过文件系统异常使SQLite backup实际拒绝目标，并验证仅清理本次目录；close错误测试在drained延后期间确认close尚未返回。不能以此自动化结果或操作矩阵替代真实界面和数据验收。


### 已知上游边界

来源生成器目前在进入内部try块前执行新目录的chmod。若这一步发生极少见的权限故障，调用方尚未收到目录，可能留下一份空临时目录；不会覆盖已有资料或启动服务。此处仅记录既有边界，后续应对生成器做独立最小修复和故障测试，不在本演练草稿中暗改其实现。
