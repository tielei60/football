# 阶段40：球员与赛季共享创建账本恢复

## 问题及实现
球员、赛季共用的创建账本原先只在内存中保留，并随登录令牌变化清空，无法跨运行窗口重开保护未知结果。

本轮为共享创建流程增加持久核对标记，按服务来源、账号、球队、业务类型隔离。标记只保存任务编号与时间，不保存表单姓名、日期、照片或令牌。有效成功与明确拒绝精确清理本任务；未知回执、过期会话回执、无效成功编号及清理失败保留提醒。球员编号按现有字符串规则验证，赛季编号验证正整数。

两页统一增加“已核对，记录已存在”入口，只解除提醒并返回各自列表，不重复创建。确认回调核对账号、任务、页面可见性、授权、编辑状态与在途请求。共享动作层区分尚未发出请求的存储失败，不把所有本地异常误判为已发送；过期会话回执不清理新会话。

## 原生验证
使用新建匿名演练数据库、仅回环地址故障代理和专用微信开发者工具窗口：

1. 原生输入“阶段40匿名新增球员”，使用默认待定位置保存。服务端成功后代理返回502，页面进入核对状态。
2. 球员待核对期间仍可进入赛季新增，原生输入“阶段40匿名恢复赛季”，通过日期组件设置2026-11-20至2026-11-21。成功落库后同样返回502，赛季进入独立核对状态。
3. 关闭并重开专用运行窗口。两类新增表单均为空，原任务的核对提醒保留，禁止直接重复提交。
4. 先查看赛季列表，确认唯一新赛季及日期；确认“记录已存在”后赛季解除。再次打开球员新增，其核对提醒仍在，证明解除赛季没有误清球员标记。
5. 在球员列表找到唯一匿名球员，再确认解除球员提醒。两页重新打开均恢复正常空白新建表单。
6. 正常退出模拟管理员，确认登录页与数据库会话数0。

## 数据审计
球员及赛季新增接口各1次。与操作前基线逐表核对：仅club_players、club_seasons各新增1条，两个表原有记录及其余业务表均不变。没有新增账号、照片、比赛或报名。本轮匿名球队不触发球队1的战术桌同步规则，不将该分支描述为本轮原生覆盖。

## 检查结果
- 最终小程序测试1313项通过，官方模板虚拟渲染140次通过。
- 后端235项通过，app构建通过。
- 新增34项专项回归，涵盖两个类型、独立模块重启与同账号新令牌、来源/账号/球队隔离、旧回执和旧确认、存储写入/读回/清理故障、明确拒绝、异常成功编号、在途/隐藏/销毁/编辑状态以及照片与私有草稿不持久化。
- 既有管理页面测试保留原断言，只补真实会话身份和内存存储适配；同账号新令牌现在仍需核对，真正跨账号用不同用户编号验证。
- 已独立复查共享影响范围，团队资料更新及既有编辑PUT未改为创建流程。

## 限制与现场
实际跨运行验证为专用窗口关闭重开，不是手机系统重启。账号/来源/球队隔离和存储异常由控制器测试覆盖，不冒充原生逐项故障实测。两类表单恢复提醒但不恢复草稿；人工“未创建”需自行核对列表，保护标记不是服务端幂等证明。

原隔离配置已逐字恢复，专用窗口关闭，临时服务停止，模拟会话已撤销。用户原工作区及正式数据未改动。原生截图、请求计数、基线差异、测试与清理证据保留在本地阶段40目录，未上传数据库、真实照片或登录信息。
