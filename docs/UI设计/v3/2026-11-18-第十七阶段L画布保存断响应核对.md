# 第十七阶段 L：画布保存断响应后的核对恢复

## 隔离与方法

阶段22释放后接管专属微信开发者工具工程，新建独立匿名演练库，没有操作正式球队数据库。使用真实输入登录、真实按钮、真实画布拖动，不调用页面方法或篡改状态冒充操作。

本机一次性代理仅对第一条 `/api/tactics/1/commands` 的 PUT 做故障注入：请求完整转发；待上游返回200且响应完整读取结束后，销毁下游连接，不向小程序交付该成功回执。其他请求正常转发。日志仅记录方法、路径、上游状态和是否丢弃交付，不存请求头、正文、Cookie或令牌。没有返回伪造500，也没有将独立API的成功替代为原生写入。

## 实际覆盖

1. 真实登录匿名管理员，打开战术并进入编辑，选择直线并拖绘；读取提交前完整模型作为基准。
2. 点击保存，代理证据显示该真实 PUT 的 `upstreamStatus: 200`、`deliveryDropped: true`。页面显示保存结果需核对，完整草稿保持，原版本未擅自更新，保存和编辑工具被禁用。
3. 再次点击禁用保存，未产生第二条 PUT。
4. 点击核对重新载入后取消，完整草稿与提交前一致，冲突保护保留，没有新增战术GET。
5. 再次点击核对并确定，正常读取已经保存的最新版本，退出编辑/冲突状态。完整画布与提交前草稿一致，完整模型及版本散列与数据库一致。

## 数据和请求审计

- 全程只有一次目标PUT，上游200并断下游交付；没有重复写入。
- 取消前只有初始战术GET，确认后才增加一次GET。
- 保存后恰好增加一条历史快照，内容等于最终画布；原历史保持，重载没有新增快照。
- 初始球员、原标注、演示动画和曲线、比赛附加信息均保持；新增直线的标识在最终记录中只出现一次。
- 其他业务表与基线逐表核对一致。认证运行表另行处理，正常退出后 `club_sessions = 0`。
- 审计脚本实际执行通过，不仅靠截图或记录数量推断。

本地证据目录：`football-ui-v3-interaction/tactic-stage17l`。包括一次性代理脚本、完整模型、请求状态日志、`audit.mjs`、`audit.json`、`unknown.png`、`reloaded.png`及`completed.json`。运行数据库、凭据清单与截图不提交仓库。

## 安全收尾与限制

真实退出确认后回到登录页；核对本批配置归属后逐字节恢复；关闭s2窗口；停止匿名服务和代理，确认拥有的进程消失。没有修改产品源码，也没有配置密钥或对外发送数据。

本批证明的是“服务端已提交成功但客户端没有收到回执”的同页核对恢复。没有覆盖请求根本未到达服务端、跨进程草稿保存、真机后台切换、全部网络故障时序。不能由本次通过宣称所有未知结果均能自动恢复；当前流程仍要求用户明确核对并确认重载。
