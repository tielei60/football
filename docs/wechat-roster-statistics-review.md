# 小程序赛季名单、比赛快照与统计：匿名实测记录

## 范围与初始状态

本轮使用新的全匿名副本。赛季 1 初始 revision=2，含 P1、P2 两人，赛季号码及当前球员号码均为 1、2。比赛 1 初始为 published、revision=1、比分为空、比赛名单为空。来源库不参与修改；版本通过正常保存递增，不做回滚。以下操作均区分实际 UI 与独立后台核验。

## 号码零值与比赛历史快照

1. 实际在赛季名单将 P1 号码改为 0，保存并重入；赛季 revision=3，仅赛季 P1 号码变化，当前球员号码仍为 1。
2. 实际将比赛设为完赛、比分 0:0，保存重入；比赛 revision=2，仅状态、比分及 revision 改变。
3. 实际添加 P1 为首发并确认出场，进球、助攻留空（null）；P2 为替补并确认出场，进球、助攻显式为 0。仅保存一次后重入，比赛 revision=3，历史名单号码为 0、2。

新增名单草稿时，P1 最初显示当前号码 1，保存后显示赛季号码 0。这是实测发现的预览来源不一致，保存数据正确。只读源码核对：服务端按已有历史快照 → 赛季名单 → 当前球员取值，而前端新增行直接采用当前球员。当轮尚未实施修复；后续已实现最小预览修正，同实例连续保存的有限实测见[比赛名单草稿身份预览修正](wechat-match-roster-preview-review.md)，不改写本轮发现。

## 空值、零值与统计口径

独立 SQL 核验为 1 场、1 平、总比分 0:0；两人出场均为 1。P1 的进球及助攻为 null，known=0；P2 两项均为 0，known=1，未将未知成绩当成明确零值。

实际查看默认 2026 年及选择赛季 1 后的各三张榜单，并分别查看两种范围下的 P1、P2 详情，共 6 张榜单与 4 次详情。口径、破折号与 0 的显示，以及 known 字段一致。默认年份来自实际页面，不是人为改年构造结果。

## 赛季移除与重新加入的隔离性

实际移除赛季 P1 时先取消，后台 24 张表无写入。再次确认并保存重入，赛季 revision=4，仅保留 P2；比赛历史名单完整行及其他 22 张表不变。

在新页面实例重新加入 P1，不改默认号码 1，保存重入后赛季 revision=5。按球员 ID 对齐核验，两条赛季名单完整内容与最初号码 1、2 的状态一致；比赛历史名单仍保留号码 0、2。实际重新查看赛季三张榜单，统计未漂移。上述版本递增是正常保存结果，不宣称恢复了初始 revision。

## 数据恢复与验证边界

实际通过 UI 删除两名比赛名单成员并保存，重入确认名单为空；此时比赛 revision=4，仍为 completed、比分 0:0。比分清空因开发者工具键盘焦点异常未完成，未将该异常归为产品缺陷，也不记为 UI 清空通过。

随后仅对本轮匿名副本，通过正常 `saveMatch` CAS 恢复比赛为 published、比分为 NULL，revision 正常增至 5。独立核验完整比赛行与初始状态仅 revision 不同，其余 23 张表与恢复前一致，来源库 24 张表不变；赛季仍为 revision=5，成员内容保持原样。这是业务层数据收尾，不是 UI 清空操作成功，也没有回退版本。

最终实际通过首页图标离开旧稿，未出现确认框且未保存；再从“我的”退出并确认，恢复至 375 宽度空登录页。会话数为 0；比赛完整行与初始值仅 revision 从 1 增至 5 不同，保持 published、NULL 比分及空名单；赛季仅 revision 从 2 增至 5。

赛季名单按 playerId 对齐的两条完整记录均与初始号码 1、2 一致，但物理插入行序不同，不能声称该表摘要与初始完全相同。其余 21 张表与初始摘要一致，来源库 24 张表不变，CAS 恢复后的 23 张业务表无额外写入。配置经双 SHA 守卫恢复原字节，本轮服务执行会话 exit 0、对应端口无监听，环境收尾完成。

新增名单号码预览问题后续已实现最小修复，并完成有限同实例保存及重入检查，详见[专项记录](wechat-match-roster-preview-review.md)。本记录不等同于全部统计组合、真机或所有名单生命周期通过。
